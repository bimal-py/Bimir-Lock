# Store automation — Bimir Lock

Fastlane drives both listings from files in this repo, the same way it does for
Callbreak (`../callbreaktracker/FASTLANE.md`). Nothing is submitted for review
automatically: every lane leaves a draft for a human to press the button on.

## The normal cycle

```sh
# 1. edit the copy
$EDITOR listing/v2/en/…            # then re-transcreate the locales

# 2. check it before it goes anywhere
python3 tool/check_listing.py

# 3. copy it into the two fastlane trees
python3 tool/assemble_listing.py

# 4. screenshots (once the raw captures exist — see listing/shots/README.md)
../marketing/.venv/bin/python tool/make_screenshots.py --all --install

# 5. read the stores back, so you know what you are about to change
cd android && bundle exec fastlane probe
cd ../ios  && bundle exec fastlane probe

# 6. dry run
cd ../android && bundle exec fastlane upload_listing validate:true

# 7. upload
cd ../android && bundle exec fastlane upload_listing      # text only
cd ../android && bundle exec fastlane upload_images       # icon, feature graphic, screenshots
cd ../ios     && bundle exec fastlane ensure_edit_version version:1.1.1
cd ../ios     && bundle exec fastlane upload_listing      # text + screenshots
```

## Lanes

**Android** (`cd android`): `probe`, `tracks`, `images` (live graphics vs disk, by checksum), `download_listing`,
`download_store_details`, `upload_listing`, `upload_images`, `upload_changelogs`,
`deploy` (uploads an AAB you already built as a **draft** release — it never builds).

**iOS** (`cd ios`): `probe`, `probe_live`, `locales`, `download_listing`,
`ensure_edit_version`, `upload_listing`, `upload_release_notes`,
`upload_version_copy`, `pull_live_copy`.

## Traps (all inherited from Callbreak, all learned the hard way)

**Play has no draft state for listing text.** An edit is either uncommitted and
invisible or committed and in review. `hold:true` maps to the Play API's
`changesNotSentForReview`, which only applies *when a rejection happens* — on an
app in good standing Google accepts the parameter, ignores it, and sends the
change to review anyway. Managed publishing is the control that actually works,
and it is Console-only. Turn it on before the v2 upload if you want the listing
and the 1.1.1 build to go live together.

**`supply` is destructive to screenshots.** `sync_image_upload` defaults to
false, so `upload_images` deletes the remote set for a locale before uploading
the local one. Whatever is on disk becomes live. Locales with no local
screenshots are skipped rather than wiped.

**The first iOS version is "1.0" in App Store Connect; the binary is 1.1.1.**
Run `ensure_edit_version version:1.1.1` once — it renames the draft so the build
you upload matches.

**A name or subtitle change goes through review with the binary.** On iOS, use
`upload_release_notes` / `upload_version_copy` for later What's New and promo
text edits instead of replaying `upload_listing`.

**Neither store's "success" means anything.** Both tools print success for
values that did not apply. After every upload, run `probe` and read the state back.

## Snapshotting a version

Before changing anything live, put the current listing somewhere it cannot be
overwritten:

```sh
cd ios && bundle exec fastlane download_listing
cd ../android && bundle exec fastlane download_listing && bundle exec fastlane download_store_details
mkdir -p listing/v3/{ios,android}
cp -R ios/fastlane/metadata listing/v3/ios/
cp -R android/fastlane/metadata/android/. listing/v3/android/
```

`download_listing` overwrites the working folders, so snapshot first. (This is
how `listing/v1/` was made.)
